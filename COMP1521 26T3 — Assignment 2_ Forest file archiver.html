Aims

  • building a concrete understanding of file system objects;
  • practising C, including byte-level operations and robust error handling;
  • understanding file operations, including input-output operations on binary data

The Task

A file archive is a single file which can contain the contents, names and other metadata of multiple files. These can make backup and transport of files more convenient, and can often make compression more efficient. We often refer to tools that can create or manipulate these as file archivers.

There are a vast number of archive formats: on *nix-like systems, tar is common; whereas on Windows, Zip is common. Wikipedia's list of archive formats is a marvellous rabbit-hole to explore.

In this assignment, you will be implementing forest, a file archiver for the tree format.

The tree format is made up of one or more leafs; where a leaf records one file system object; This format is described in more detail below.

A complete implementation of forest can

  • list the path names of each object in a tree (subset 0);

  • list the permissions of each object in a tree (subset 0);

  • list the size (number of bytes) of files in a tree (subset 0);

  • check the leaf magic number (subset 0);

  • extract files from a tree (subset 1);

  • check a tree for integrity, by checking leaf hashes; (subset 1);

  • set the file permissions of files extracted from a tree (subset 1);

  • create a tree from a list of files (subset 2);

  • list, extract, and create trees that include directories (subset 3); and

  • extract, and create trees in 7-bit and 6-bit formats (subset 3).

The tree and leaf format

trees must follow exactly the format produced by the reference implementation.

A tree consists of a sequence of one or more leafs. Each leaf contains the information about one file or directory.

The first byte of a tree file is the first byte of the first leaf. That leaf is immediately followed by either another leaf, or by the end of the tree file.

name length type description
magic number 1 B unsigned, 8-bit, little-endian byte 0 in every leaf must be 0x63 (ASCII 'c')
leaf format 1 B unsigned, 8-bit, little-endian byte 1 in every leaf must be one of 0x36, 0x37, 0x38 (ASCII '6', '7', '8')
permissions 10 B characters bytes 2—11 are the type and permissions as a ls-like character array; e.g., "-rwxr-xr-x"
pathname length 2 B unsigned, 16-bit, little-endian bytes 12—13 are an unsigned 2-byte (16-bit) little-endian integer, giving the length of
pathname pathname-length characters the filename of the object in this leaf.
content length 6 B unsigned, 48-bit, little-endian the next bytes are an unsigned 6-byte (48-bit) little-endian integer giving the length of the file that was encoded to give
content content-length for 8-bit format, see below for other formats bytes the data of the object in this leaf.
hash 1 B unsigned, 8-bit, little-endian the last byte of a leaf is a leaf-hash of all bytes of this leaf except this byte.

leaf content encodings (Subset 3 only)

  • 8-bit format (leaf format == 0x38 contents is an array of bytes, which are exactly equivalent to the bytes in the original file.

  • 7-bit format (leaf format == 0x37) contents is an array of bytes representing packed seven-bit values, with the trailing bits set to zero. Every byte of the original file is taken as a seven-bit value, and packed as described below. This format can store any seven bit value — so, for example, any byte containing valid ASCII can be stored.

    This format needs ⌈(7.0/8)∗content-length⌉⌈(7.0/8)∗content-length⌉ bytes. 7-bit format is used only in subset 3.

  • 6-bit format (leaf format == 0x36) contents is an array of bytes of packed six-bit values where the trailing bits in the last byte are zero, and which are translated using the functions tree_to_6_bit and tree_from_6_bit in forest_6_bit.c.

    This format cannot store all ASCII values, for example upper case letters can't be stored in 6-bit format.

    This format needs ⌈(6.0/8)∗content-length⌉⌈(6.0/8)∗content-length⌉ bytes.

7-bit and 6-bit format is used only in subset 3.

Packed n-bit encoding (Subset 3 only)

We often store smaller values inside larger types. For example, the integer 42 only needs six bits; but we often will store it in a full thirty-two-bit integer, wasting many bits of zeroes. Assuming we know how many bits the value needs, we could only store the relevant bits.

For example, let's say we have three seven-bit values a, b, c, made up of arbitrary bit-strings, and stored in eight-bit variables

  • a: 0b0AAA_AAAA,
  • b: 0b0BBB_BBBB,
  • c: 0b0CCC_CCCC,
then a packed seven-bit encoding of these values in order would be: 
0bAAAA_AAAB_BBBB_BBCC_CCCC_C???

However, we have a problem: what happens to the trailing bits, which don't have a value? Note that we've defined all trailing bits to be zero above, which would here give: 

0bAAAA_AAAB_BBBB_BBCC_CCCC_C000

Each line of hexdump output is in three groups:

  • the address column: this starts at 0x00000000, and increases by 0x10 (or 16 in base 10) each line;

  • the data columns: after the address, we get (up to) 16 two-digit hexadecimal values, grouped into two blocks of eight values each, which represents the actual data of the file, and

  • the human readable stripe: at the very end of each line, between the vertical bars (|) is the human readable version of the bytes preceding, or a '.' if the byte wouldn't ordinarily be visible.

6-bit format (Subset 3 only)

leaf 6-bit format defines a subset of 64 8-bit values (bytes) to have a six-bit encoding; those six bits are then stored packed.

The remaining 192 8-bit values can not be encoded in 6-bit format.

The functions tree_to_6_bit and tree_from_6_bit in forest_6_bit.c to convert 8-bit values to and from 6-bit format.

You can find the mapping by reading the code in forest_6_bit.c.

The leaf hash (Subsets 1, 2, 3)

Each leaf ends with a hash (sometimes referred to as a digest) which calculated from the other values of the leaf. This allows us to detect if any bytes of the tree have changed, for example by disk or network errors.

The tree_hash() function makes one step of computation of the hash of a sequence of bytes: 

uint8_t tree_hash(uint8_t current_hash_value, uint8_t byte_value) {
    return ((current_hash_value * 33) & 0xff) ^ byte_value;
}

Given the hash value of the sequence up to this byte, and the value of this byte it calculates the new hash value.

If we create a tree of a single one-byte file, like this: 

echo >a
1521 forest -c a.tree a

We can then inspect the tree, and see its hash is 0x15. 

hexdump -Cv a.tree
00000000 63 38 2d 72 77 2d 72 2d 2d 72 2d 2d 01 00 61 01 |c8-rw-r--r--..a.|
00000010 00 00 00 00 00 0a 15 |.......|
00000017

Here's the sequence of calls that calculated that value: 

tree_hash(0x00, 0x63) = 0x63
tree_hash(0x63, 0x38) = 0xfb
tree_hash(0xfb, 0x2d) = 0x76
tree_hash(0x76, 0x72) = 0x44
tree_hash(0x44, 0x77) = 0xb3
tree_hash(0xb3, 0x2d) = 0x3e
tree_hash(0x3e, 0x72) = 0x8c
tree_hash(0x8c, 0x2d) = 0x21
tree_hash(0x21, 0x2d) = 0x6c
tree_hash(0x6c, 0x72) = 0x9e
tree_hash(0x9e, 0x2d) = 0x73
tree_hash(0x73, 0x2d) = 0xfe
tree_hash(0xfe, 0x01) = 0xbf
tree_hash(0xbf, 0x00) = 0x9f
tree_hash(0x9f, 0x61) = 0x1e
tree_hash(0x1e, 0x01) = 0xdf
tree_hash(0xdf, 0x00) = 0xbf
tree_hash(0xbf, 0x00) = 0x9f
tree_hash(0x9f, 0x00) = 0x7f
tree_hash(0x7f, 0x00) = 0x5f
tree_hash(0x5f, 0x00) = 0x3f
tree_hash(0x3f, 0x0a) = 0x15

Assumptions and Clarifications

Like all good programmers, you should make as few assumptions as possible. If in doubt, match the output of the reference implementation.

  • Your submitted code must be a single C program only. You may not submit code in other languages.

  • You can call functions from the C standard library available by default on CSE Linux systems: including, e.g., stdio.h, stdlib.h, string.h, math.h, assert.h.

  • We will compile your code with dcc when marking. Run-time errors from illegal or invalid C will cause your code to fail automarking (and will likely result in you losing marks).

  • Your program must not require extra compile options. It must compile successfully with: 

    dcc *.c -o forest

  • You may not use functions from other libraries. In other words, you cannot use the dcc -l flag.

  • If your program prints debugging output, it will fail automarking tests. Make sure you disable any debugging output before submission.

  • You may not create or use temporary files.

  • You may not create subprocesses: you may not use posix_spawn, posix_spawnp, system, popen, fork, vfork, clone, or any of the exec* family of functions, like execve.

  • You may assume that the length of a tree is less than the maximum value supported by a long.

  • forest only has to handle ordinary files and directories.

    forest does not have to handle symbolic links, devices or other special files.

    forest will not be given directories containing symbolic links, devices or other special files.

    forest does not have to handle hard links.

  • If completing a forest command would produce multiple errors, you may produce any of the errors and stop.

    In this case you do not have to produce the particular error that the reference implementation does.

  • If a leaf path name contains a directory then a leaf for the directory will appear in the tree beforehand.

    For example, if there is a leaf for the path name a/b/file.txt then there will be preceding leafs for the directories a and a/b,

    You may also assume the leaf for the directory specifies the directory is writable.

  • When adding an entire directory (subset 3) to a tree you may add the directory contents in any order to the tree, after the directory leaf.

    You do not have to match the order the reference implementation uses.

  • When a forest command specifies adding files with a common sub-directory. You may add a leaf for the sub-directory multiple times. For example, given this command: 

    ./forest -c a.tree b/file1 b/file2
    You may add two (duplicate) leafs for b.

  • You can assume the path name of a tree being created with -c, will not also be added to the tree, and will not be in a directory being added to the tree.

  • It is not necessary to check the hashes or magic numbers of leafs in subset 0. Subset 0 tests will only use valid leafs.

  • The reference implementation checks the magic number (first byte), format and hash when listing (-l and -L) and extracting (-x) trees and stops with an error message if they are are invalid, for example: 

    ./forest -l examples/text_file.bad_hash.tree
error: incorrect leaf hash 0x2d should be 0x77
./forest -L examples/text_file.bad_magic.tree
error: incorrect first leaf byte: 0x39 should be 0x63

    This is very desirable behaviour and you can implement this in your code. However it will not be tested with -l, -L and -x command line options to avoid problems in automarking.

    Your code will only be tested with the -C option on trees with invalid hashes, magic numbers and formats

  • It is not necessary to check the hashes or magic numbers in an existing tree when appending to it (-a).
